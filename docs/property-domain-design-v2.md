# سند طراحی نهایی دامنه املاک V2

**نام پروژه:** کلارخانه — وب‌سایت حرفه‌ای املاک
**نسخه سند:** 1.0
**تاریخ:** ۱۴۰۵/۰۵/۱۳
**وضعیت:** آماده تأیید پیش از پیاده‌سازی

---

## 1. هدف سند

هدف این سند، تثبیت ساختار نهایی سه بخش اصلی V2 پیش از ایجاد Migration است:

1. مشاوران (`Agent`)
2. پروژه‌های ساختمانی (`DevelopmentProject`)
3. املاک (`Property`)

این طراحی باید نیازهای یک وب‌سایت حرفه‌ای و قابل فروش برای یک دفتر املاک، سازنده یا مجموعه فروش پروژه را پوشش دهد؛ بدون اینکه قابلیت‌های CRM کامل یا معماری چندمشتری V3 زودتر از زمان لازم وارد پروژه شود.

---

## 2. اصول قطعی طراحی

1. وضعیت انتشار از وضعیت تجاری یا اجرایی جدا باشد.
2. آدرس عمومی از آدرس خصوصی جدا باشد.
3. حذف مشاور یا پروژه باعث حذف ملک نشود.
4. هر ملک حداکثر به یک پروژه متصل باشد.
5. هر پروژه بتواند چند ملک یا واحد وابسته داشته باشد.
6. اطلاعات تماس مالک در سایت عمومی نمایش داده نشود.
7. قیمت فروش، ودیعه و اجاره ماهانه در فیلدهای جدا ذخیره شوند.
8. مدل‌ها برای پنل مدیریت قابل فهم و برای توسعه آینده قابل نگهداری باشند.
9. امکانات CRM کامل، حسابداری، قرارداد و چندشعبه‌ای در V2 وارد نشوند.
10. اعتبارسنجی‌های مهم هم در مدل و هم در فرم مدیریتی اعمال شوند.

# 4. طراحی نهایی Agent

## 4.1 هدف

مدل `Agent` در V2 یک پروفایل عمومی و مدیریتی برای مشاور است، نه حساب کاربری ورود به سیستم.

## 4.2 فیلدهای نهایی

|---|---|---:|---|
| `full_name` | `CharField(150)` | بله | نام کامل مشاور |
| `slug` | `SlugField(170, unique=True)` | بله | نشانی صفحه عمومی مشاور |
| `job_title` | `CharField(120)` | خیر | عنوان شغلی |
| `specialties` | `CharField(250)` | خیر | تخصص‌ها به‌صورت متن کوتاه |
| `short_bio` | `CharField(250)` | خیر | معرفی کوتاه برای کارت مشاور |
| `bio` | `TextField` | خیر | معرفی کامل مشاور |
| `photo` | `ImageField` | خیر | تصویر مشاور |
| `phone` | `CharField(30)` | خیر | شماره تماس عمومی |
| `rubika_url` | `URLField` | خیر | لینک عمومی پروفایل یا کانال روبیکا |
| `email` | `EmailField` | خیر | ایمیل عمومی |
| `service_regions` | `ManyToManyField(Region)` | خیر | مناطق فعالیت مشاور |
| `experience_years` | `PositiveSmallIntegerField` | بله | تعداد سال‌های سابقه |
| `instagram_url` | `URLField` | خیر | لینک اینستاگرام |
| `linkedin_url` | `URLField` | خیر | لینک لینکدین |
| `is_featured` | `BooleanField` | بله | نمایش مشاور در بخش ویژه |
| `is_active` | `BooleanField` | بله | فعال بودن پروفایل عمومی |
| `display_order` | `PositiveSmallIntegerField` | بله | ترتیب نمایش |

## 4.3 اعتبارسنجی اطلاعات تماس

برای مشاور فعال، حداقل یکی از موارد زیر باید ثبت شود:

- شماره تلفن
- لینک روبیکا
- ایمیل

شماره تلفن فقط می‌تواند شامل موارد زیر باشد:

- اعداد فارسی یا انگلیسی
- فاصله
- علامت `+`
- خط تیره
- پرانتز

مقدار `rubika_url` باید یک URL معتبر باشد؛ مانند:

```text
https://rubika.ir/username
```

## 4.4 مناطق فعالیت

هر مشاور می‌تواند در چند منطقه فعالیت داشته باشد و هر منطقه نیز می‌تواند چند مشاور داشته باشد.

نوع رابطه:

```text
Agent <-> Region
Many-to-Many
```

نام فیلد:

```python
service_regions
```

## 4.5 وضعیت فعال

مقدار `is_active=True` به این معناست که:

- مشاور می‌تواند در صفحات عمومی نمایش داده شود.
- مشاور می‌تواند به ملک‌ها و پروژه‌های جدید اختصاص داده شود.
- اطلاعات عمومی مشاور برای کاربران قابل مشاهده است.

مقدار `is_active=False` به این معناست که:

- اطلاعات مشاور حذف نمی‌شود.
- ارتباط او با ملک‌ها و پروژه‌های قبلی حفظ می‌شود.
- در صفحات عمومی نمایش داده نمی‌شود.
- در انتخاب‌های عادی پنل مدیریت پیشنهاد نمی‌شود.

## 4.6 تصمیم‌های خارج از محدوده V2

در V2 این موارد به مدل مشاور اضافه نمی‌شوند:

- اتصال مستقیم به مدل `User`
- حساب ورود اختصاصی مشاور
- داشبورد اختصاصی
- مدیریت مشتریان
- برنامه پیگیری
- وظایف مشاور
- پورسانت
- حسابداری
- گزارش عملکرد

این امکانات در صورت نیاز واقعی در V2.5 بررسی می‌شوند.

# 5. طراحی نهایی DevelopmentProject

## 5.1 هدف

مدل `DevelopmentProject` برای معرفی پروژه‌های ساختمانی، شهرک‌ها، مجتمع‌ها و طرح‌های در حال ساخت استفاده می‌شود.

هر پروژه می‌تواند چند ملک یا واحد وابسته داشته باشد.

## 5.2 جداسازی وضعیت‌ها

وضعیت ساخت پروژه و وضعیت انتشار آن باید مستقل باشند.

### ConstructionStatus

```text
planning
under_construction
completed
on_hold
```

معانی:

| مقدار | عنوان |
|---|---|
| `planning` | در مرحله برنامه‌ریزی |
| `under_construction` | در حال ساخت |
| `completed` | تکمیل‌شده |
| `on_hold` | متوقف‌شده |

### PublicationStatus

```text
draft
pending_review
published
archived
```

معانی:

| مقدار | عنوان |
|---|---|
| `draft` | پیش‌نویس |
| `pending_review` | در انتظار بررسی |
| `published` | منتشرشده |
| `archived` | بایگانی‌شده |

یک پروژه می‌تواند هم‌زمان:

```text
construction_status = under_construction
publication_status = published
```

باشد.

## 5.4 موقعیت پروژه

اطلاعات موقعیت پروژه به دو قسمت تقسیم می‌شوند:

### موقعیت عمومی

```python
public_location
```

نمونه:

```text
اسپندکلا، محدوده جاده اصلی
```

این مقدار می‌تواند در صفحه عمومی نمایش داده شود.

### آدرس خصوصی

```python
private_address
```

نمونه:

```text
کوچه، پلاک، مسیر دقیق دسترسی و توضیحات داخلی
```

این مقدار فقط در پنل مدیریت قابل مشاهده است.

## 5.5 اعتبارسنجی تعداد واحدها

این حالت نباید قابل ثبت باشد:

```text
total_units = 10
available_units = 15
```

قانون:

```text
available_units <= total_units
```

اگر یکی از دو مقدار خالی باشد، اعتبارسنجی مربوط به مقایسه اجرا نمی‌شود.

## 5.6 اعتبارسنجی تاریخ‌ها

این حالت نباید قابل ثبت باشد:

```text
start_date = 2027-01-01
expected_completion_date = 2026-01-01
```

قانون:

```text
expected_completion_date >= start_date
```

اعتبارسنجی فقط زمانی اجرا می‌شود که هر دو تاریخ مقدار داشته باشند.

## 5.7 اعتبارسنجی قیمت پروژه

در وضعیت پیش‌نویس، پروژه می‌تواند موقتاً بدون قیمت باشد.

هنگام انتشار:

- اگر `price_on_request=True` باشد، `starting_price` الزامی نیست.
- اگر `price_on_request=False` باشد، `starting_price` باید مقدار داشته باشد.
- قیمت منفی مجاز نیست.

## 5.8 درصد پیشرفت

مقدار `completion_percentage` باید بین صفر و صد باشد:

```text
0 <= completion_percentage <= 100
```

## 5.9 انتشار پروژه

هنگام انتشار پروژه:

```text
publication_status = published
published_at = current_time
```

اگر پروژه قبلاً منتشر شده باشد، تاریخ انتشار اولیه حفظ می‌شود.

هنگام انتقال پروژه به پیش‌نویس:

```text
publication_status = draft
published_at = null
```

## 5.10 متدهای دامنه پروژه

مدل پروژه باید متدهای زیر را داشته باشد:

```text
publish()
move_to_draft()
archive()
```

### publish

- وضعیت انتشار را روی `published` قرار می‌دهد.
- در صورت خالی بودن، `published_at` را تنظیم می‌کند.

### move_to_draft

- وضعیت انتشار را روی `draft` قرار می‌دهد.
- `published_at` را خالی می‌کند.

### archive

- وضعیت انتشار را روی `archived` قرار می‌دهد.
- اطلاعات پروژه حذف نمی‌شوند.

## 5.11 رابطه پروژه با ملک

هر پروژه می‌تواند چند ملک داشته باشد:

```text
DevelopmentProject
└── properties
```

هر ملک حداکثر می‌تواند به یک پروژه متصل شود.

## 5.12 موارد خارج از محدوده V2

این موارد فعلاً برای پروژه ساخته نمی‌شوند:

- مدل مستقل سازنده
- فازهای متعدد پروژه
- جدول اقساط
- مدیریت پرداخت
- قرارداد واحدها
- مدل جداگانه پیچیده برای واحدها
- پیمانکاران
- تأمین‌کنندگان
- داشبورد سازنده
- حساب کاربری توسعه‌دهنده

در V2، هر واحد قابل فروش به‌صورت یک `Property` ثبت می‌شود و به پروژه متصل خواهد شد.

# 6. طراحی نهایی Property

## 6.1 هدف

مدل `Property` هسته اصلی وب‌سایت است و باید بتواند انواع فایل‌های ملکی مستقل یا وابسته به پروژه را مدیریت کند.

نمونه‌ها:

- ویلا
- زمین
- آپارتمان
- واحد تجاری
- واحد پروژه ساختمانی
- باغ
- خانه روستایی

## 6.2 وضعیت انتشار

وضعیت انتشار فقط مشخص می‌کند که ملک در سایت عمومی قابل مشاهده است یا خیر.

### PublicationStatus

```text
draft
pending_review
published
archived
```

معانی:

| مقدار | عنوان |
|---|---|
| `draft` | پیش‌نویس |
| `pending_review` | در انتظار بررسی |
| `published` | منتشرشده |
| `archived` | بایگانی‌شده |

## 6.3 وضعیت دسترسی یا نتیجه معامله

وضعیت معامله باید از وضعیت انتشار جدا باشد.

### AvailabilityStatus

```text
available
reserved
sold
rented
unavailable
```

معانی:

| مقدار | عنوان |
|---|---|
| `available` | موجود |
| `reserved` | رزروشده |
| `sold` | فروخته‌شده |
| `rented` | اجاره‌رفته |
| `unavailable` | موقتاً غیرفعال |

یک ملک فروخته‌شده می‌تواند برای نمونه‌کار در سایت منتشر باقی بماند؛ اما نباید در فهرست پیش‌فرض املاک موجود نمایش داده شود.

## 6.4 نوع معامله

### TransactionType

```text
sale
rent
mortgage_rent
full_mortgage
pre_sale
```

معانی:

| مقدار | عنوان |
|---|---|
| `sale` | فروش |
| `rent` | اجاره |
| `mortgage_rent` | رهن و اجاره |
| `full_mortgage` | رهن کامل |
| `pre_sale` | پیش‌فروش |

## 6.5 اطلاعات قیمت

فیلد واحد قدیمی زیر:

```python
price
```

حذف می‌شود و با فیلدهای جداگانه جایگزین خواهد شد.

| فیلد | کاربرد |
|---|---|
| `sale_price` | قیمت فروش یا پیش‌فروش |
| `deposit_amount` | مبلغ ودیعه یا رهن |
| `monthly_rent` | اجاره ماهانه |
| `currency_code` | واحد پول |
| `price_on_request` | قیمت توافقی یا تماس بگیرید |
| `is_price_negotiable` | قابل مذاکره بودن قیمت |

## 6.6 قواعد قیمت

قواعد اجباری قیمت هنگام انتشار اعمال می‌شوند. ملک پیش‌نویس می‌تواند موقتاً ناقص باشد.

### فروش

```text
transaction_type = sale
```

باید یکی از شرایط زیر برقرار باشد:

```text
sale_price دارای مقدار باشد
```

یا:

```text
price_on_request = True
```

### پیش‌فروش

```text
transaction_type = pre_sale
```

باید یکی از شرایط زیر برقرار باشد:

```text
sale_price دارای مقدار باشد
```

یا:

```text
price_on_request = True
```

### اجاره

```text
transaction_type = rent
```

قواعد:

- `monthly_rent` باید مقدار داشته باشد.
- `deposit_amount` می‌تواند خالی یا صفر باشد.
- در صورت `price_on_request=True`، قیمت‌ها می‌توانند خالی باشند.

### رهن و اجاره

```text
transaction_type = mortgage_rent
```

قواعد:

- `deposit_amount` باید مقدار داشته باشد.
- `monthly_rent` باید مقدار داشته باشد.
- در صورت `price_on_request=True`، قیمت‌ها می‌توانند خالی باشند.

### رهن کامل

```text
transaction_type = full_mortgage
```

قواعد:

- `deposit_amount` باید مقدار داشته باشد.
- `monthly_rent` باید خالی یا صفر باشد.
- در صورت `price_on_request=True`، مبلغ رهن می‌تواند خالی باشد.

### قواعد عمومی قیمت

- هیچ مبلغی نمی‌تواند منفی باشد.
- قیمت‌های نامرتبط با نوع معامله نباید به‌صورت اشتباه نمایش داده شوند.
- قیمت توافقی باید با عبارت واضح در سایت نمایش داده شود.
- وضعیت قابل مذاکره بودن باید جدا از قیمت توافقی باشد.

## 6.7 رفتار فیلتر قیمت

فیلتر قیمت باید وابسته به نوع معامله باشد.

### فروش و پیش‌فروش


### رهن کامل

فیلتر براساس:

```text

```

```text
monthly_rent
```


بعد از تغییر مدل بازطراحی خواهند شد.

## 6.11 ارتباط ملک با پروژه

فیلد پیشنهادی:

```python
project = models.ForeignKey(
    "projects.DevelopmentProject",
    on_delete=models.SET_NULL,
    related_name="properties",
    null=True,
    blank=True,
)
```

قواعد:

- اتصال ملک به پروژه اختیاری است.
- هر ملک حداکثر متعلق به یک پروژه است.
- حذف پروژه نباید باعث حذف ملک شود.
- در صورت حذف پروژه، مقدار `project` ملک خالی می‌شود.
- منطقه ملک و پروژه باید یکسان باشد.

این حالت نامعتبر است:

```text
Property.region = اسپندکلا
Project.region = رودبارک
```

سیستم نباید منطقه ملک را به‌صورت پنهانی تغییر دهد؛ بلکه باید خطای اعتبارسنجی نمایش دهد.

## 6.14 اعتبارسنجی تصویر کاور

وجود تصویر کاور هنگام انتشار لازم است؛ اما این قانون نباید داخل متد `clean()` مدل `Property` قرار بگیرد.

دلیل:

- تصویرها از طریق Inline پنل مدیریت ثبت می‌شوند.
- خود ملک پیش از ذخیره Inlineها ذخیره می‌شود.
- در زمان اجرای `clean()` ممکن است تصویر هنوز در دیتابیس ثبت نشده باشد.

بررسی تصویر کاور باید در یکی از قسمت‌های زیر انجام شود:

- فرم مدیریتی اختصاصی
- سرویس انتشار
- عملیات انتشار در Admin
- متد کنترل‌شده انتشار

هر ملک عمومی باید حداکثر یک تصویر کاور داشته باشد.

## 6.15 مشاور مسئول

وجود مشاور مسئول برای ملک منتشرشده بسیار مطلوب است؛ اما در V2 محدودیت سخت دیتابیس نیست.

رفتار پیشنهادی:

- ملک بدون مشاور می‌تواند ذخیره شود.
- هنگام انتشار، Admin هشدار نمایش دهد.
- در صفحه عمومی، در صورت نبود مشاور، اطلاعات تماس عمومی مجموعه نمایش داده شود.

## 6.16 قواعد نمایش عمومی

فهرست پیش‌فرض سایت فقط املاکی را نمایش می‌دهد که شرایط زیر را داشته باشند:

```text
publication_status = published
```

و:

```text
availability_status in [available, reserved]
```

املاک زیر در فهرست پیش‌فرض نمایش داده نمی‌شوند:

```text
sold
rented
unavailable
```

نمایش املاک فروخته‌شده یا اجاره‌رفته فقط در صورت طراحی بخش جداگانه «معاملات انجام‌شده» انجام خواهد شد.

## 6.17 انتشار ملک

هنگام انتشار:

```text
publication_status = published
published_at = current_time
```

اگر ملک قبلاً منتشر شده باشد، تاریخ انتشار اولیه حفظ می‌شود.

هنگام انتقال به پیش‌نویس:

```text
publication_status = draft
published_at = null
```

## 6.18 متدهای دامنه ملک

مدل یا سرویس دامنه باید عملیات زیر را پشتیبانی کند:

```text
publish()
move_to_draft()
archive()
mark_as_reserved()
mark_as_sold()
mark_as_rented()
mark_as_unavailable()
```
